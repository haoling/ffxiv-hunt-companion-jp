# FFXIV Hunt Companion JP 開発計画書

## 1. 概要と結論

モブハントのデイリー／ウィークリー手配書をスマホのカメラで読み取り、次のことをするモバイル向け Web サイトを作る。

- 対象モブの名前・エリア・地域名・討伐数を一覧にする
- 対象が FATE のボスなら、その FATE 名を案内する
- 出発する街を選べるようにして、効率のよい回り方を**文字で**案内する
- 倒し終えたモブにチェックを入れて、完了表示にする

**結論: 実現できる。** サーバーは不要で、今のスケルトン（Next.js の静的エクスポート＋GitHub Pages）のまま作れる。

- ゲームのクライアントデータに、モブハント専用のシート（`MobHuntTarget` / `MobHuntOrder` / `MobHuntOrderType`）がある。
  **「どのモブが、どのエリアの、どの地域にいるか」「FATE のボスかどうか、その FATE はどれか」がデータとして引ける。**
- 地域名（例:「サゴリー砂漠」）の地図上の位置は `MapMarker` から、エーテライトの位置は `Aetheryte` と `MapMarker` から取れる。これでルートを計算できる。
- いちばん不確実なのは**カメラ撮影からの文字認識（OCR）の精度**。
  認識結果を「既知のモブ名辞書」とのあいまい一致で補正し、候補から選び直せる UI を用意すれば実用になる見込み。

## 2. 要件ごとの実現方法

| # | 要件 | 実現方法 | データソース | 難易度 |
|---|---|---|---|---|
| 1 | 手配書をカメラで認識してモブ名・エリアを抽出 | `getUserMedia` で撮影（画像アップロードも可）→ Tesseract.js（jpn）で OCR → モブ名辞書とあいまい一致 → 確認・修正 UI | `MobHuntTarget` → `BNpcName` | **高**（精度がいちばんのリスク） |
| 2 | FATE ボスなら FATE 名を案内 | `MobHuntTarget.FATE` が 0 以外なら FATE の対象として、`Fate.Name` を表示 | `MobHuntTarget.FATE` → `Fate` | 低 |
| 3 | エリアとおおよその位置から最適ルート | エリアごとにまとめ、エーテライトを起点にエリア内の回る順番を最適化 | `Map`、`MapMarker`、`Aetheryte`、FATE の座標は Teamcraft の `fates.json`（M0 で変更） | 中 |
| 4 | ルートは文字で表示 | 「テレポ先 → 地域名 → 対象」の手順リストを出す | 上と同じ | 低 |
| 5 | 位置は地域名＋湧き位置の中心座標で表示 | `MobHuntTarget.PlaceName`（手配書の「生息場所」と同じ）を使う。FATE の対象も同じ（FATE の座標はルート計算だけに使う）。実測のある通常モブは、Teamcraft の `monsters.json` から出した湧き位置の中心座標も添える（§5.3） | `PlaceName`、`MapMarker`、Teamcraft `monsters.json` | 低 |
| 6 | 出発地をハント受注できる街から選ぶ | 街の一覧を持ち、各街のエーテライトを起点にする | 手で管理する街リスト＋`Aetheryte` | 低 |
| 7 | 倒し終えたら手動でチェック | チェックボックス＋`localStorage` に保存。リセット時刻（次の受注が可能になる時刻）を表示 | — | 低 |
| 8 | 移動方法の好み（テレポ優先／飛行移動／徒歩移動）を個人設定で選ぶ | エリア同士のつながり（地上で行けるか、飛行が必要か）をグラフとして持ち、設定に応じてルート計算の移動手段を切り替える（§8.1） | `MapMarker`（エリアの出口）＋手で管理する補正リスト | 中 |

## 3. 手配書の仕様（前提）

### 3.1 種類

- **デイリー手配書**: 拡張ごとにレベル別の手配書がある。1 枚に対象が複数あり、UI ではページ送り（例: `4/5`）で 1 体ずつ表示される。
- **ウィークリー手配書（エリートモブ）**: 週に 1 回受注する。対象は B モブで、決まった湧き地点候補のどこかに出る。

添付画像（新生エオルゼアの不滅隊の手配書）の下部パネルに出る情報:

```
モブ手配書                       4/5
討伐対象   ウルハドシ
討伐体数   1
生息場所   南ザナラーン サゴリー砂漠
討伐報酬   ギル:2,000 同盟記章:20
発行公証人 不滅隊局長 ラウバーン・アルディン
```

→ OCR で読むのは**この下部パネルだけ**でよい。上の羊皮紙風の部分は装飾文字で読めないので使わない。
`生息場所` に「エリア名＋地域名」がそのまま出るのが大きい。

### 3.2 ハントを受注できる街と出発地の候補

手配書を受注できる場所（M0 でゲームデータから確認。[M0 レポート §5](./m0/REPORT.md#5-手配書の受注場所)）:

| 拡張 | 受注場所 |
|---|---|
| 新生エオルゼア | リムサ・ロミンサ（黒渦団）／グリダニア（双蛇党）／ウルダハ（不滅隊）のモブハントボード ※所属するグランドカンパニーの本部だけ |
| 蒼天のイシュガルド | イシュガルド：下層（初級・中級・リスキーモブ）／イディルシャイア（上級） |
| 紅蓮のリベレーター | クガネ |
| 漆黒のヴィランズ | クリスタリウム |
| 暁月のフィナーレ | オールド・シャーレアン |
| 黄金のレガシー | トライヨラ |

出発地の候補は、受注場所に加えて各拡張の主な拠点（ラールガーズリーチ、ユールモア、ラザハン、ソリューション・ナイン）も選べるようにする。
出発地は受注場所と同じでなくてもよい（受注後にテレポしてから回り始めるケースに対応する）。
設定で「最後に使った出発地」を覚えておく。

## 4. アーキテクチャ

- **フロントエンド**: 今の Next.js 16（App Router、`output: "export"`）＋ React 19。全部クライアント側で処理する。
- **ホスティング**: GitHub Pages（既存の `.github/workflows/deploy.yml` をそのまま使う）。
- **データ**: ビルド時に生成した JSON（`public/data/hunts.json`）を同梱し、実行時に外部 API へアクセスしない。
- **OCR**: Tesseract.js（WASM）。`jpn` の学習データは数 MB あるので、スキャン画面を開いたときに遅延読み込みし、Service Worker でキャッシュする。

```
[カメラ/画像] → [切り出し・前処理] → [Tesseract.js] → [辞書照合] → [確認・修正UI]
                                                                  ↓
                          [チェック状態(localStorage)] ← [対象リスト] → [ルート計算] → [文字のルート表示]
                                                                  ↑
                                                    [hunts.json（ビルド時に生成）]
```

## 5. データパイプライン

### 5.1 使うシート

`xivapi/ffxiv-datamining` の CSV（日本語）を取り込む。スキーマは `xivdev/EXDSchema` で確認済み。

| シート | 使う列 | 用途 |
|---|---|---|
| `MobHuntTarget` | `Name`→BNpcName, `FATE`→Fate, `Map`→Map, `PlaceName`→PlaceName, `Icon` | 対象モブの本体データ |
| `MobHuntOrder` | `Target`, `NeededKills`, `Type`, `Rank`, `MobHuntReward` | 手配書ごとの対象と討伐数 |
| `MobHuntOrderType` | `Quest`, `EventItem`, `OrderStart`, `Type`, `OrderAmount` | デイリー／エリートの区別、どの拡張の手配書か |
| `BNpcName` | `Singular` | モブ名（OCR 辞書） |
| `Fate` | `Name` | FATE 名 |
| `Map` | `SizeFactor`, `OffsetX/Y`, `PlaceName`, `TerritoryType`, `MapMarkerRange` | 座標変換、エリア名、MapMarker の範囲 |
| `MapMarker` | `PlaceNameSubtext`, `X`, `Y`, `DataType`, `DataKey` | 地域名ラベル（`DataType` 0）、エリアの出口（1 → Map）、エーテライト（3 → Aetheryte）、エーテネット（4 → PlaceName）の位置。2 は ID ダンジョンなどの入口で使わない |
| `Aetheryte` | `PlaceName`, `Territory`, `Map`, `IsAetheryte` | テレポ先 |
| `PlaceName` | `Name` | 地域名・エリア名 |
| `TerritoryType` | `ExVersion` | エリアがどの拡張か |
| `Quest` / `ENpcResident` / `Level` | `IssuerStart`, `IssuerLocation` / `Singular` / `X`, `Z`, `Map` | 手配書の受注 NPC とその位置 |

**M0 で分かったこと**: `Fate.Location` と `Aetheryte.Level[0]` が指す ID は Level シートに無い（ゲームのレイアウトファイル側の ID）。
そのため FATE の座標は Teamcraft の `fates.json`（MIT、`position` の `map` / `x` / `y`）から取り、エーテライトの位置は `MapMarker`（`DataType` 3）から取る。
Teamcraft に位置が無い FATE（今は FATE 238 の 1 件だけ）は、`MobHuntTarget.PlaceName` の地域名ラベルの位置で代用する。

### 5.2 生成スクリプト

- `scripts/build-data.ts`（Node 22.18 以上。`npm run build:data`）で CSV を読み、`public/data/hunts.json` を出力する。手順は [M1 レポート](./m1/REPORT.md)。
- 生成した JSON はリポジトリに commit する（ビルドのたびに外部から取得しない）。パッチが来たら手動で再生成する。
- 座標変換（ゲーム内のマップ座標にそろえる）:
  - `Level` の座標: `c = SizeFactor / 100`、`mapX = 41 / c * ((X + OffsetX) * c + 1024) / 2048 + 1`（Z も同様）
  - `MapMarker` の座標: テクスチャ上のピクセル位置なので `mapX = 41 / c * X / 2048 + 1`
  - どちらも M0 で検証済み（Level の式は NPC 2 万件あまりで誤差 0.01、MapMarker の式はエーテライト 107 件で誤差 0.35 以内。[M0 レポート §3](./m0/REPORT.md#3-座標変換)）。
- エリアのつながり（テレポせずに移動できるか）:
  - `MapMarker` のうち、隣のエリアへの出口を示すマーカー（`DataType` 1、`DataKey` が行き先の Map）から「エリア A の出口 (x, y) → エリア B」を取り出す。
  - 行き先がフィールドか街でないもの（ハウジングエリア、PvP、コンテンツの入口）は除く。街を通らないと行けないエリアが多いので、街の地図もグラフに入れる（街の地図にも出口のマーカーがある）。
  - 出口の反対側の到着位置は、エリア B 側にある「A へ戻る出口」のマーカーの位置で代用する。
  - データから取れない・誤っているつながり（例: 飛行しないと渡れない、クエスト進行で開く、船や定期便でしか行けない。M0 で船・定期便も出口として入っていることを確認した）は、手で管理する補正リスト（`scripts/zone-links.overrides.json`、`remove` / `requiresFlying` / `add`）で追加・削除する。
  - 各つながりに「飛行が必要か」（`requiresFlying`）の印を付ける。データからは判別できないので、補正リストで指定する（既定は「地上で行ける」）。
  - **徒歩＝地上をマウントで移動する**、**飛行＝飛行マウントで移動する**と定義する。船や定期便でしか行けない区間はどちらにも含めない。

### 5.3 位置の精度についての方針

- 通常モブの湧き位置は**ゲームデータに無い**（サーバー側で決まる）。
  そこで `MobHuntTarget.PlaceName` の**地域名ラベルの位置**を「おおよその位置」として扱う。
- FATE ボスは Teamcraft の `fates.json` の座標をルート計算に使う。表示する地域名は、手配書と同じ `MobHuntTarget.PlaceName` にする
  （M0 で、FATE の位置にいちばん近い地域名ラベルは 95 件中 72 件で手配書の表示と違うことが分かったため）。
- エリート（B モブ）は湧き地点が複数あり、`MobHuntTarget.PlaceName` も 0（地域名なし）なので、表示は「エリア名」だけにする。
  あとで HuntHelper の湧き地点データ（MIT）を取り込んで候補を出せるようにする（任意）。
- 地域名ラベルだけでは、ツインプールズのような広い地域でモブを見つけにくい。
  そこで Teamcraft の `monsters.json`（MIT、実測の湧き位置。キーは BNpcName ID）を取り込み、モブごとに**湧き位置の中心座標**（最大 3 か所、実測点が多い順）を `HuntTarget.spawns` に入れる。
  - 使う点は、対象の `Map` と一致し、`fate` が 0 の点だけ。重複は除き、4 マス以内の点を 1 つのまとまりにして中心と件数を出す。
  - 地域名ラベルから 12 マス以内にまとまりがあればそれだけを使う（無ければ全部）。最大のまとまりの 15% 未満は捨てる。
  - ルート計算は「FATE → 湧き位置の中心 → 地域名ラベル → エリア中央」の順で位置を決める。中心が 4 マス以内の対象は同じ立ち寄り先にまとめる。
  - 画面では「地域名 (x, y) 付近」と表示する。実測データの無いモブは従来どおり地域名だけ。

## 6. データモデル（案）

```ts
// 実際の型は app/lib/hunt-types.ts（ここは概要）
type HuntTarget = {
  id: number;             // MobHuntTarget の行 ID
  name: string;           // モブ名（日本語）
  nameKana?: string;      // あいまい一致の補助（任意）
  zoneId: number;         // Map の ID
  regionId?: number;      // PlaceName の ID（地域）。エリートは地域名が無いので省略
  fate?: { id: number; name: string; x: number; y: number };
  spawns?: { x: number; y: number; n: number }[]; // 実測の湧き位置の中心（実測点が多い順）。無いモブは省略
  kind: "daily" | "elite";
  expansion: "arr" | "hw" | "sb" | "shb" | "ew" | "dt";
  orderTypeIds: number[]; // 載っている手配書の種類（OrderType.id）
  neededKills: number[];  // 手配書に書かれた討伐体数（取りうる値）
};

type Zone = { id: number; name: string; expansion: HuntTarget["expansion"]; kind: "field" | "town"; sizeFactor: number; aetherytes: number[]; exits: ZoneExit[] };
// エリアの出口（テレポせずに隣のエリアへ行ける地点）
type ZoneExit = {
  toZoneId: number;
  x: number; y: number;               // 出口の位置
  arrivalX: number; arrivalY: number; // 隣のエリアでの到着位置
  requiresFlying: boolean;            // 飛行しないと通れない出口か
};
type Region = { id: number; zoneId: number; name: string; x: number; y: number };
type Aetheryte = { id: number; zoneId: number; name: string; x: number; y: number };
type City = { id: string; name: string; aetheryteId: number; expansion: HuntTarget["expansion"] };

// 取り込んだ手配書の 1 行（ユーザーの状態）
type BillEntry = {
  targetId: number;
  neededKills: number;
  done: boolean;
  source: "ocr" | "manual";
  addedAt: string;        // ISO 日時（追加した時刻）
};

// 個人設定（localStorage に保存）
type UserSettings = {
  grandCompany?: "maelstrom" | "twinAdder" | "immortalFlames";
  defaultCityId?: string;
  travelPreference: "teleport" | "fly" | "walk"; // 既定は "teleport"（§8.1）
};
```

## 7. OCR の設計

1. **入力**: カメラのプレビュー（`getUserMedia`、背面カメラ）で撮影する。PC のスクリーンショットの取り込み（`<input type="file" accept="image/*">`）にも対応する。スクリーンショットのほうが精度はずっと高い。
2. **切り出し**: プレビューに「下部パネルをこの枠に合わせる」ガイド枠を重ね、枠の中だけを切り出す。
3. **前処理**（Canvas）: グレースケール → 2〜3 倍に拡大 → コントラスト補正 → 二値化（大津の方法）。モニターを撮ったときのモアレ対策に、軽くぼかしてから二値化する。
4. **認識**: Tesseract.js（`jpn`）。行ごとに「討伐対象」「討伐体数」「生息場所」「n/5」のラベルを手がかりに値を取り出す。
5. **正規化**: 全角・半角の統一、紛らわしい文字（`ー`/`一`、`ロ`/`口`、`カ`/`力` など）をそろえる。
6. **辞書照合**: 対象モブ名の辞書（数百件）と、文字 n-gram の類似度やレーベンシュタイン距離で照合し、上位 3 件を候補にする。「生息場所」の文字列でも照合して候補を絞る。
7. **確認・修正 UI**: 認識結果を候補つきで表示し、タップで選び直せるようにする。エリア→モブの順に選べる手入力モードも常に用意する。
8. **取り込み漏れの警告**: `n/5` を読み取り、手配書 1 枚ぶんのページがそろっていなければ知らせる。

将来の選択肢: ユーザーが自分の API キーを入れた場合だけ、画像認識できる LLM で読み取るモードを追加する（既定ではオフ）。

## 8. ルート計算

1. 選んだ街のエーテライトを出発点にする。
2. 未完了の対象をエリアごとにまとめる。
3. エリアごとに、入口にするエーテライト（エリア内の対象までの合計距離が最小になるもの）を決める。
   出発する街から歩いて行ける隣のエリア（例: ウルダハ → 西／中央ザナラーン）は「徒歩」として先に回す。
   どこまでテレポせずに移動するかは、個人設定の移動方法の好みで変わる（§8.1）。
4. エリア内の回る順番は、対象が少ない（多くても 10 前後）ので全順列で最短を探す。多いときは最近傍法＋2-opt に切り替える。
5. エリア間の順番は「徒歩で行けるエリア → 同じ拡張のエリアをまとめる」の順に並べる。エリア間をテレポ・飛行・徒歩のどれで移動するかは §8.1 の設定に従う。
6. 出力（文字のみ）:

```
出発: ウルダハ
1. テレポ: 忘れられたオアシス（南ザナラーン）
   → サゴリー砂漠（南西へ）: ウルハドシ ×1  ※FATE「砂漠の神皇帝「ウルハドシ」」のボス
   → ○○: △△ ×3  ※FATE「□□」のボス
2. テレポ: …
```

- 方角（北東へ など）は、直前の地点から次の地点へのベクトルで決める。
- FATE の対象には「FATE が発生していないときは待つか、後回しにする」と注記する。

### 8.1 移動方法の好み（テレポ優先／飛行移動／徒歩移動）

設定の `travelPreference` で、エリア間の移動手段の選び方を切り替える。

| 設定 | エリア間の移動 | 向いている人 |
|---|---|---|
| **テレポ優先**（既定） | 基本はテレポ。飛んだほうが明らかに近いとき（同じエリアの中、または隣のエリアの出口の近くにいるとき）だけ、テレポせずに移動する | 移動時間を短くしたい人 |
| **飛行移動** | 今いる場所から**テレポせずに行けるエリアは、遠くても（いくつエリアをまたいでも）飛んで行く**。飛行が必要な区間も通る。つながっていないエリア（別の大陸・島、船や定期便が必要な場所）へ行くときだけテレポする | ギルやテレポの読み込みを減らしたい人、道中の FATE やモブも拾いたい人（飛行を解放済み） |
| **徒歩移動** | 飛行移動と同じく、テレポせずに行けるエリアは遠くても移動するが、**地上を通る区間だけ**を使う。飛行が必要な区間は通らず、その先へはテレポする | 飛行をまだ解放していないエリアがある人、地上を移動したい人 |

計算方法:

1. エリアを頂点、`Zone.exits` を辺とするグラフを作る。辺の重みは「出口までのエリア内の距離」。距離はエリアごとの縮尺（`SizeFactor`）をそろえてからワールド単位で比べる。
   - 徒歩移動では `requiresFlying` の辺を除いたグラフを使う。
   - エリア内の距離は、飛行では直線距離、徒歩では地形で遠回りする分を見込んで直線距離に係数（初期値 1.3、調整可能）を掛けたものにする。
2. テレポ優先: 各エリアへの移動コストを `min(テレポの固定コスト, 飛行の最短距離)` とする。テレポの固定コストは「読み込み＋エーテライトからの移動」を距離に換算した定数（調整可能）にする。
3. 飛行移動・徒歩移動: 今いるエリアから（それぞれのグラフで）たどれる未完了のエリアがあれば、テレポのコストは使わず、最短経路でいちばん近いものへ向かう。たどれるエリアが残っていないときだけ、残りのエリアの中から入口のエーテライトを選んでテレポする。
4. どの設定でも、エリアを回る順番は「次のエリアへ行く手間」だけで決めない（近いエリアを後回しにして引き返すのを避けるため）。残りのエリアが 6 以下なら全順列を試して移動の手間の合計が最小のものを、多いときは 2 エリア先まで見て選ぶ。エリア内の回る順番の決め方（§8 の 4.）は同じ。
5. テレポせずにエリアをまたぐときは、通過するエリアと出口も手順に出す:

```
出発: ウルダハ（徒歩移動）
1. 徒歩: ウルダハ → 西ザナラーン（ウルダハ正門から）
   → ○○: △△ ×2
2. 徒歩: 西ザナラーン → 中央ザナラーン → 南ザナラーン（中央ザナラーンの南の出口から）
   → サゴリー砂漠: ウルハドシ ×1
3. テレポ: …（地上でつながっていないエリア）
```

- 飛行移動では、手順の見出しを「飛行: 」にする。
- ルート画面の上部に今の設定（テレポ優先／飛行移動／徒歩移動）を表示し、設定画面へのリンクを置く。
- 設定を変えたら、表示中のルートをその場で計算し直す（チェック状態は保持する）。

## 9. 進捗管理

- 各対象にチェックボックスを付け、チェックしたら完了表示（取り消し線、グレーアウト）にして、ルートから外す。
- チェックを入れた対象の場所（地域名の位置、FATE の位置、エリートはエリアの中央）を現在地として `localStorage` に覚え、ルートの再計算はその現在地から始める（出発地に戻って組み直さない）。現在地は、出発地を変えたとき、「完了済みを削除」「すべて削除」のとき、ルート画面の「出発地から計算し直す」で忘れる。
- 状態は `localStorage` に保存する（端末ごと。読み書きは try/catch で囲み、使えない環境でも画面は動くようにする）。
- 受注済みの手配書は、リセット時刻を過ぎても有効で、倒せば報酬ももらえる。リセットは「次の手配書を受注できるようになる時刻」なので、自動では消さない（ゲーム内で確認済み）。完了した行はユーザーが削除する（「完了済みを削除」）。リセット時刻は画面に表示する。

## 10. 画面構成

1. **ホーム**: 今日の手配書リストと進捗、「スキャン」「手入力」ボタン、出発地の選択
2. **スキャン**: カメラのプレビュー＋ガイド枠、撮影、画像の取り込み
3. **確認・修正**: 認識結果と候補、討伐数の修正、「リストに追加」
4. **ルート**: 出発地を選ぶ → 手順リスト（各行にチェックボックス）
5. **設定**: 所属グランドカンパニー、既定の出発地、移動方法の好み（テレポ優先／飛行移動／徒歩移動、§8.1）、データのバージョン表示、ライセンス表記

### 11.1 プレイヤーによるゲーム内確認

ゲームデータや机上の検証だけでは確かめられないこと（表記の一致、実際に通れる道、リセット時刻、実機での OCR など）は、プレイヤーにゲーム内で確認してもらう。

- 各マイルストーンの実装が終わったら、エージェントは上の表の「プレイヤーにゲーム内で確認してもらう項目」をもとに、**具体的なチェックリストを作ってプレイヤーに提示する**。
  - Markdown のチェックボックス（`- [ ]`）で書き、1 項目ずつ「どこで・何をして・何が見えれば OK か」がわかるようにする（例: 「受注場所で手配書を 1 枚受け取り、1 件目の『生息場所』がアプリの表示と同じか」）。
  - 確認対象は、実装やデータで不安が残るところを優先して、プレイヤーの負担が大きくならない件数に絞る。
  - チェックリストは `docs/<マイルストーン名>/CHECKLIST.md` に置き、PR 本文からもリンクする。
- プレイヤーから結果を受け取ったら、同じファイルに結果（OK／NG と気づいたこと）を書き込み、NG の項目は修正するか、§13 の未確認事項・§12 のリスクに記録する。
- ゲーム内で確認できていない項目が残っているマイルストーンは、完了扱いにしない。

## 12. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| スマホ撮影の OCR 精度が低い（モアレ、反射、傾き） | 高 | 下部パネルだけ切り出す、前処理、辞書照合、候補からの選択、手入力モード、スクショ取り込み |
| Tesseract の学習データが重い | 中 | 遅延読み込み＋Service Worker でキャッシュ。初回だけダウンロードに時間がかかる旨を表示する |
| パッチで対象や名前が変わる | 中 | 生成スクリプトで再生成できるようにし、データのバージョンを画面に出す |
| 地域名ラベルの位置と実際の湧き位置がずれる | 低〜中 | Teamcraft の実測座標から湧き位置の中心を出して表示する（§5.3）。実測データが無いモブは「おおよその位置」と明記する |
| 新生エオルゼアの手配書は所属グランドカンパニーでしか受注できない | 低 | 設定で所属を選び、出発地の候補を絞る |
| エリアのつながりや「飛行が必要か」のデータが不完全で、飛行移動・徒歩移動のルートが実際には通れない | 中 | 補正リストで直す。テレポしない区間の手順には通過するエリアと出口を必ず出し、ユーザーが誤りに気づけるようにする |
| データの利用条件 | 中 | 非商用、`© SQUARE ENIX` 表記、MIT データのクレジット |

## 13. 未確認事項

M0 で確認した結果（詳細は [M0 レポート](./m0/REPORT.md)）:

- ✅ `MobHuntTarget.PlaceName` は、デイリーの対象ではすべて地域名（エリア名になっているものは無い）。
- ✅ エリートの対象は `Map` だけが入っていて、`PlaceName` は 0。
- ✅ `MobHuntOrderType`: `Type` 1 = デイリー、2 = エリート。22 種類の手配書と拡張の対応は M0 レポート §1。
- ✅ ページ数: デイリーはすべて 5 ページ、エリートは 1 ページ。
- ✅ `Level` と `MapMarker` の座標変換式は正しい。
- ❌ `Fate.Location` → `Level` では FATE の座標が取れない → Teamcraft の `fates.json` を使う（§5.1）。
- ✅ エリアの出口は `MapMarker.DataType` 1。船・定期便、ハウジングエリア、コンテンツの入口も入っているので補正リストで除く。
- ✅ 各拡張の手配書の受注場所と最寄りのエーテライト／エーテネット（§3.2、M0 レポート §5）。

まだ確認していないこと:

- ✅ 飛行移動のルート、操作性（スマホでの手入力→ルート→チェック、再読み込み後の保持）。ゲーム内で確認済み（[M2 チェックリスト](./m2/CHECKLIST.md)）。徒歩移動はゲーム内で検証できなかったが、ヨシとした。
- ✅ デイリー／ウィークリーのリセット時刻（日次は 15:00 UTC = 0:00 JST、週次は火曜 8:00 UTC = 17:00 JST）。ゲーム内で確認済み（[M2 チェックリスト](./m2/CHECKLIST.md)）。
- ✅ 飛行しないと通れない出口の洗い出しと、船・定期便の区間の補正リストの中身（M1 でゲーム内確認済み。飛行が必要なのは、クルザス西部高地 ↔ アバラシア雲海だけ。[M1 チェックリスト](./m1/CHECKLIST.md)）。ただし確認したのは、新生〜紅蓮の補正リストに載せた区間と気になった出口の範囲）。
